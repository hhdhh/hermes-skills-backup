# 太空舱取货链路与"不抓取"排查

## 完整链路
订单商品代码写入黑板 → PreloadOrder / ReadOrderDatabase → 调整机身高度并导航至商品路点 → 移动头部、识别商品（按失败计数重试）→ 抓取 → 回前台 → 放置 → TTS → ready。

"不抓取"是链路末端表现，先定位卡在哪一段，再动对应模块。

## 分型排查表

| 现象 | 卡点 | 归因模块 | 排查动作 |
|---|---|---|---|
| 下单后机器人不动 | 任务没下发 | 业务层 | 查商品—Quest—Workflow 映射、服务器状态、机器人绑定、KioskApp ID |
| 到货架前停住、不伸手 | 识别失败 | AI / dataset | 见下"识别分支" |
| 识别到了但臂/爪无动作 | 执行层 | arm / 夹爪 / 急停 | 读夹爪状态反馈；查急停是否触发未复位；不连续重发 |
| 动了但抓空、抓偏 | 参数/标定 | dataset / 定位 | 先排除定位偏差（归 GV/SLAM），再调 dataset grasp 参数 |

## 任务下发分支
- ReadOrderDatabase 用黑板里的商品名去 dataset 目录找 config：**商品名与 dataset 目录名必须严格一致**——差一个字符就读不到，现象即不下发/不抓。

## 识别分支（最常见）
1. 先确认真的"到位"：小车到位异常归 GV/SLAM，先重定位。**定位或路点偏差过大时继续调末端抓取参数会掩盖根因**。
2. `ai-grasp-service` 是否 active；不 active 查 snack 环境日志与权重，**禁止直接启动 Flow**。
3. `vision-service`：ai-grasp 强依赖 vision。相机无帧先做只读读帧验证，不切未验证相机。
4. dataset 三件套：**参考图片 + 形状 OBJ 文件 + config.json**，必须匹配实际现场；参考图要用现场成功识别的实时图片替换（换环境后老图识别率下降）。
5. CPU 过热会被 Doctor 阻断放行（有 101°C 阻断先例）——先散热再核功能。

## 执行层分支
- 夹爪命令退出码 0 ≠ 真动了：读状态反馈，必要时整机复位，不连续重发。
- 相机无帧：查服务状态和相机脚本，不切到未验证的相机。

## dataset / XML 参数生效三坑（改了不生效先查这里）
1. **真正生效的是 `dataset` 目录，不是 `dataset_example`**——改错目录是最常见事故。
2. **改 XML 必须重启 flow；改 dataset 热生效**。
3. XML 里需有 `InitializeDataset` + `ReadOrderDatabase` 且输入参数连通，少一个改了也不生效；**config 里有参数但 XML 没传入 → 不生效**；XML 有 config 没有 → 报错或走默认值。

## 场景适配（配置文档）
- 取杯器上方透明盖：换识别参考图与 OBJ 模型 + 减少取杯器内杯量保抓取稳定。
- 咖啡机识别依赖额外 3D 打印的顶部定位方块——无该模块的项目提前定制硬件。
- 咖啡场景共 4 次识别（取杯/咖啡机定位/杯盖/取餐），比冰淇淋链路长；识别失败先数卡在第几次识别。
