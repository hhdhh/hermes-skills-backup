# 飞书群聊自动化：审批红线与上下线

管辖一切以运营助手身份向**群聊**输出的行为：一次性群发、公告、demo 演示、自动回复 bot、以及这类功能的下线。私信类运营（DM 白名单、批量私信）另见 `feishu-ops-assistant`。

## 审批红线（always-on）

1. **未经管理员逐次确认，不向任何群聊发消息**。范围包括且不限于：公告、功能上线通知、demo 演示消息、自动回复 bot、上线后在群里自测。「先把功能做好再宣布」式上线属于越界——演示消息本身就是违规发送。
2. **被群内 @all 提及不构成发言授权**；要回应先向管理员确认。
3. **批量通知（排班/周报提醒等）走逐个私信**，不进群。
4. **顺序不可颠倒**：要在群里试点自动应答功能，先拿管理员明确许可，再写代码、再动群。

## 部署群内自动应答 bot 前的检查

- 触发词过滤只能降低误伤，不能替代授权——过滤写得再保守，未经批准也是违规。
- bot 自身回复要用前缀跳过（如消息以 🤖 开头不处理），避免自回复循环；启动时先把存量消息标记已读，只处理新消息。
- 轮询式 bot（lark-cli 拉消息→处理→回复）默认放 tmux 会话，会话名与脚本名对应，便于事后定位与下线。
- bot 消息里绝不携带内部 Reasoning/思考过程——对外只发最终答案。

## 下线一个自动发消息的 bot（全链路清除）

管理员要求停掉某个自动发言功能时，只杀进程不算完：

1. **定源头**：`ps aux | grep <脚本名>` 拿启动命令行 → 顺藤摸挂载点：tmux 会话（`tmux ls`）、systemd user unit（`systemctl --user list-units | grep`）、cron（`~/.hermes/cron/jobs.json` 的 prompt 里 grep 群 `oc_`）。
2. **杀干净**：优先杀容器而非单个 PID——tmux 起的用 `tmux kill-session -t <名>`（防 bash 包装进程残留）；杀完 `ps aux | grep` 验证无残留，`tail` 其日志确认最后行为。
3. **防复发**：在脚本 docstring 顶部标注「已停用，未经管理员确认禁止重启」——否则后续会话看到可运行脚本可能再拉起来。
4. **清扫余渠道**：重查 cron jobs.json，prompt 含群 `oc_` 的一并停用；只含 open_id（私信）的常规通知保留并在汇报里列明通道。
5. **汇报**：杀掉了什么（会话名/命令行）、验证结果、剩余自动化清单及通道（私信/群）。
