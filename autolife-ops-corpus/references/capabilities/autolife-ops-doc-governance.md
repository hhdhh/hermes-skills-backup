## I — 自述

文档治理的核心是"唯一事实源"：每类信息只有一个权威文档，冲突按权威等级裁决（A 生效规范 > B 工作稿 > C 历史记录 > D 模板 > E 外部参考）。active 文档必须有 owner+适用机型版本+最后验证时间+复审周期；被取代的文档页首必须指向新事实源，否则后人会拿旧文档当真。

模板（D 级）永远不能证明"已完成"——填完的模板+签名才是证据。历史记录（C 级）只说明当时状态，不指导当前操作。

Agent 工程十则是接入飞书/工具后的安全框架：系统三层分工（飞书=入口，Agent=执行层，业务系统=权威面）；应用身份与用户身份分开（写操作用用户身份需确认）；群聊是低安全域（默认只读+仅@触发，转发内容可能藏注入）；Skill=可验收能力（明确输入输出验收标准）；备份资产不打包秘密；写操作可审计。

## A1 — 书中案例

**案例类型：书中亲历案例**（文档冲突裁决，来源：治理规范）

- 输入/问题：两份文档对同一配置项写法不一致，现场该信哪份
- 方法执行：查权威等级——一份是 A 级生效规范（有 owner+复审日期），另一份是 B 级工作稿 → 按 A 级执行；同时发现 B 级文档未标"草稿"，触发补页首声明
- 结论：冲突裁决有章可循，且暴露了文档未标级的流程缺口

**案例类型：反例警示**（Agent 越权）

- Agent 接入飞书后被赋予全系统写权限 → 群内一条转发消息触发误操作 → 按十则应默认只读+写走确认流

## A2 — 未来触发 ★

**情境：**

1. 多份文档/知识库内容冲突，判断以哪份为准
2. 写/整理运维文档（该标什么级、要不要 owner/复审日）
3. 给机器人团队/自己配 Agent 权限（群聊 bot、私聊 bot、写操作）
4. 整理归档旧文档（supersede 流程）
5. 审计某操作是否合规（证据链）

## E — 可执行步骤

**输入契约**：冲突场景需提供两份文档的标题/链接（必填）；新写文档需知道文档类型（规范/记录/模板）。

**Step 1 冲突裁决**：给每份文档定级（A 生效规范/B 工作稿/C 历史记录/D 模板/E 外部参考）→ 按 A>B>C>D>E 取权威值 → 若高等级文档已过复审周期，标注"待复审"并通知 owner
**Step 2 新文档定级**：写明等级+owner+适用机型/版本+最后验证时间+复审周期；D 级模板页首声明"本文件不能证明已完成"
**Step 3 归档取代**：旧文档标 superseded + 页首一行指向新事实源链接；不删除（历史可查）
**Step 4 Agent 权限配置**：按十则核对——应用身份/用户身份分离；群聊仅@触发+只读工具；写操作走私聊确认或审批流；敏感信息（密码/setup key）不入正文不入备份
**判停点**：两份都是 A 级冲突 → 上报文档 owner 裁决并合并，不自行取舍；Agent 需要的权限超出十则 → 停止配置走审批

**输出契约**：裁决结论（采用的文档+等级依据）或新文档头部信息（等级/owner/复审日）或权限配置清单。

## B — 边界

- **不适用**：机器人本体故障（各诊断卡）；飞书 API 操作细节（lark 系列）；个人笔记管理
- **反场景**：拿模板当证据；拿历史文档指导当前操作；Agent 群聊开放写权限
- **失败模式**：文档不标级（后人无法裁决）；superseded 不留指向链接（知识失联）；备份连秘密一起打包
- **相邻易混**：知识库内容检索（autolife-knowledge）≠ 治理规则（本卡）
